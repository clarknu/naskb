## 0. 结论速览

1. **前提纠偏**：「API 输入输出都要企业版」不准确，且已到源码级确认。**输出侧**（应用对话，
   OpenAI 兼容 `/api/application/{id}/chat/completions` + 应用 API Key）在社区版直接可用
   （v1 开发手册原文写明，v2 源码路由与社区实测均证实）；专业版卖的是**平台级「开放 API」SDK**
   这层产品化包装。至于**输入侧**（建库/传文档的管理 API）：代码在开源仓库里**完整存在**
   （v2 为 `/admin/api/*`，内置 Swagger `/admin/api-doc` 可自查），只是官方不公开文档、
   不承诺契约稳定——社区已有直接调用批量导入的实践。
2. 因此「API 输入」有三条递进路：界面手动导入（零风险）→ 直调管理 REST API 半自动同步
   （加适配层锁版本）→ fork 封一层自己的稳定管理 API（Plan B）。注意社区版的硬上限：
   **50 知识库 / 5 应用 / 2 用户**——「多用户」恰恰也是它收费的功能点之一。
3. **法律边界**：MaxKB 社区版是 **GPLv3**（另附飞致云社区协议：不得使用其商标/Logo/产品名、
   不授予企业版权利）。「只要不整体破解就没事」这个理解需要修正——GPL 的红线不在
   「整体 vs 部分」，而在「**是否分发**」+「是否构成衍生作品」。好消息是你的全部设想场景
   （内网自部署 + HTTP 调用 + 改源码自用）都在安全区内；真正危险的动作（把它的代码抄进
   NASKB 再对外分发）恰好是你没打算做的。另经源码树遍历确认：**企业版功能根本不在开源
   仓库里**（独立闭源包 + license 校验动态加载），不存在「破解解锁」的对象。
4. **路线判断**：组件拆解（路线 D）性价比最低——MaxKB 的底层几乎全是宽松许可的第三方上游
   （Django BSD / langchain MIT / pypdf BSD / pgvector…），自研的是分段策略、检索融合等
   **GPLv3 应用层代码**，拆代码不如用上游；学设计可以，搬代码不行。
   **页面整合（B）只能当赠品不能当主菜**；fork 补丁（C）是备胎；**独立实例 + API 整合（A）
   是主线**。
5. **一个此前被忽略的近道（D'，推荐先做）**：「标准/规范类文档」的深度分析差距，本质是 NASKB
   没有 chunk 级检索（REQ-R2-03 一文件一向量）。利用已有的 MinerU Markdown 产物按标题层级分段、
   在 PG 向量库里加 chunk 行做「文件级找文档 + 条款级找位置」双层检索，可以在**不引入任何外部
   系统**的前提下补掉大部分差距。MaxKB/替代品的触发条件后移到「需要工作流编排/多用户运营/
   现成界面」真正出现时。
6. **替代品事实**：「API 收费」是 MaxKB 特有问题，不是品类问题——RAGFlow（纯 Apache 2.0）、
   Dify、FastGPT、AnythingLLM（MIT）开源版的 API 全部免费全量开放。若追求标准类复杂版式解析
   质量，RAGFlow DeepDoc 一枝独秀，代价是 ≥4 核 16GB 的部署门槛。

## 1. 问题定义：所谓「深度分析」缺的到底是什么

### 1.1 NASKB 现有检索模型的定位

现行模型（ADR-20260811-1、REQ-R2-01/03）：

- 索引只用 AI 生成的**摘要+描述**（summary/category/tags/content_description），一个文件一条向量；
- 全文提取后只作为 RAG 生成阶段的上下文（Doc.text/context 分层），不参与召回。

这是一个**文件发现模型**：「哪份文件和我问的事有关」回答得很好；但对「实施标准里 6.3.2 条
原文怎么规定的」「这份规范的表 4 中耐压要求是多少」这类**条款级问题**，召回粒度太粗——
一份 300 页的标准只有一个向量，代表不了其中某一条。

### 1.2 目标文档的特征（项目/研发文档、行业/实施标准）

| 特征 | 对检索的要求 | 现状缺口 |
|---|---|---|
| 条款编号体系（章/节/条） | 按标题层级分块，块内保留条款号上下文 | 无 chunking（REQ-R2-03） |
| 大量表格（参数/指标） | 表格结构识别，表题随行 | PyMuPDF/MinerU 有产物，但未到检索层 |
| 扫描件 | OCR 后同样要分块 | MinerU 已解决解析，缺分块入库 |
| 跨页长条款 | 块间重叠/父子块（child 命中→parent 上下文） | 无 |
| 精确出处引用 | 答案引用到「文件+条款」两级 | 现有 sources 只到文件路径 |

**结论：差距集中在「chunk 级精细 RAG」一段，而不是文件管理、OCR、多模态——后者 NASKB 反而更强**
（MinerU 全格式、MiMo 图片音频、音视频分级，恰是 ADR-20260816-1 里说的「MaxKB 短板恰是 NASKB 已做的部分」）。
这个判断决定了后面所有路线的取舍。

## 2. MaxKB 事实核查（整合设计的地基）

### 2.1 许可证与版本结构

- 社区版许可证：**GPLv3 全文**（GitHub 1Panel-dev/MaxKB，默认分支 v2，~22.6k★/3.1k fork，
  最新 v2.10.5-lts）。
- 飞致云《社区软件许可协议》在 GPLv3 之上追加：免费安装使用；**未经书面授权不得使用其
  商标/Logo/产品名**；**不授予商业版/企业版任何权利**；无质保；争议适用中国大陆法律。
  （厂商另口径称「商用需商业授权」——对纯内网自用无影响；若未来对外提供产品化服务需重新评估。）
- 社区版容量上限（官方价格表）：**50 知识库 / 5 应用 / 2 用户**。
- 专业版 ¥4.8 万/套：飞书知识库同步、问答页身份验证、企微/钉钉/飞书/Slack 接入、自定义
  Logo、SSO（LDAP/OIDC/CAS/OAuth2）、操作日志、**开放 API（平台级 SDK）**、ARM 包；
  企业版（2025-07 发布）再加多租户/完整 RBAC/集群。
- **企业版功能不在开源仓库**（已遍历 v1/v2 源码树确认）：无 x-pack 后端模块，仅前端占位
  与 license 校验接口——企业功能为独立闭源包 + license 动态加载。**不存在「改代码解锁
  企业功能」这回事**，fork 的意义只能是「自己补一层自己的 API」（见路线 C）。

### 2.2 API 能力的真实分布（关键纠偏，源码级核实）

| 能力 | 归属 | 证据 |
|---|---|---|
| **应用对话 API**：OpenAI 兼容 `/api/application/{id}/chat/completions`（`Bearer application-xxx`），含工作流应用、MCP 节点调用 | **社区版可用** | v1 开发手册原文「MaxKB 创建的应用支持通过 OpenAI SDK 格式…接入，专业版在社区版基础上提供平台级的完整 SDK」；v2 源码 `apps/chat/urls.py` 含 `chat/completions` 等路由；社区帖实测可调通 |
| **嵌入第三方**（全屏/浮窗/移动端） | 社区版可用 | 官方价格表明确列入社区版 |
| 工作流编排（含 MCP 节点）、Web 站点同步 | 社区版可用 | 官方价格表 |
| **管理 REST API**（建库、文档导入、触发向量化等）：v2 挂在 `/admin/api/*`（v1 为 `/api/*`），内置 Swagger（`/admin/api-doc`）可查全部接口；登录会话/token 认证 | **代码完整存在于开源仓库**，但属非公开契约——无官方文档、无稳定性承诺；官方收费的「开放 API」是平台级 SDK 这层产品化包装 | v2 源码 `apps/knowledge/api/document.py` 等含导入接口；社区有直调批量导入实践 |
| 开放 API / 平台级系统 SDK、SSO/LDAP、操作日志、问答页身份验证、自定义 Logo | 专业版付费项 | 官方价格表 |
| 多租户 / 完整 RBAC / 集群 | 企业版 | 官方价格表 |

> 含义：**「问」（输出）免费且官方支持；「管」（输入）的接口就在你部署的开源实例里，
> 直调可行但自担版本风险**。你要整合的两件事都不构成硬障碍。（注：MaxKB 文档旧路径
> `/docs/v2/` 已 404，现行文档在 `maxkb.cn/docs/`。）

### 2.3 技术栈构成：哪些是它的，哪些是别人的（源码核实）

| 层 | 技术 | 来源属性 |
|---|---|---|
| 后端 | Python 3.11 + Django 5.2/DRF + Celery/Redis 异步；Swagger（drf-spectacular） | 第三方开源（BSD 类） |
| RAG 编排 | langchain / langgraph / MCP 接入；检索+重排在 `apps/application/flow/step_node/` | langchain MIT；编排自研 |
| 向量库 | PostgreSQL + pgvector（`blend_search.sql` 混合检索 + jieba 分词） | 第三方开源（PostgreSQL License） |
| 文档解析 | **pypdf**（PDF，自研目录/链接感知分段）、python-docx、openpyxl、beautifulsoup4——**未用 unstructured**；分段器 `common/utils/split_model.py` | 解析库宽松许可；**分段策略自研（GPLv3）** |
| 嵌入服务 | sentence-transformers 独立本地服务（端口 11636）；模型接入层 `apps/models_provider/impl/` | 各模型自有许可证 |
| 前端 | Vue3 + Vite 双 SPA（管理端/聊天嵌入端）+ LogicFlow 工作流画布 | Vue3 MIT |
| **MaxKB 自研价值** | **知识库/应用数据模型、分段策略与参数体系、混合检索融合、工作流编辑器、双 SPA 界面** | GPLv3 |

**判断：底层件全是宽松许可的上游；自研的是「分段策略 + 检索融合 + 编排」这类应用层设计——
值得读、不值得搬。** 模块边界清晰（`apps/common/handle/impl/`、`apps/knowledge/task/`），
作为设计参考材料质量很高（DeepWiki 有 AI 整理的代码导读），但这不改变 GPLv3 约束：学设计合法，
拷代码进 NASKB 有传染风险（§3）。

## 3. 法律边界：GPLv3 之下每个设想动作的合规性

先修正一个认知：**「不整体、完整地破解就没有法律问题」不成立**。GPLv3 的约束逻辑是：

1. **触发点是「分发（convey）」，不是「使用」**——内部部署、内网访问、通过 HTTP 调用，
   都不触发任何源码义务；AGPL 才管网络服务，GPLv3 不管。
2. **衍生作品的判定看「拷贝/修改了受保护代码」**——抄一段它的代码进你的闭源程序再分发，
   和整体拷贝再分发，性质相同，都违反 GPLv3。「只拿了一部分」不是抗辩理由。

逐动作判定（对应本问题的全部设想）：

| # | 动作 | 判定 | 说明 |
|---|---|---|---|
| 1 | 自部署 MaxKB 社区版，内部使用 | ✅ 完全自由 | GPL 经典场景，零义务（保留版权声明的惯例照做） |
| 2 | 你的系统通过 HTTP 调它的 API（公开的应用 API 或内部 REST API） | ✅ 安全 | 进程间通信＝独立程序的聚合（mere aggregation），不构成衍生作品；这也是所有商用系统对接 GPL 服务的标准姿势 |
| 3 | 修改/增补它的源码，自己部署自用 | ✅ 安全 | 不分发即无公开义务；建议保留原版权与许可证文件，改动记录留档 |
| 4 | fork 改造后对外提供/分发（哪怕免费） | ⚠️ 义务触发 | 整体须以 GPLv3 提供，包括你新增的部分 |
| 5 | 把它的源码片段摘进 NASKB，NASKB 仅内部使用不分发 | 🟡 低风险但不推荐 | 无分发则无强制公开义务，但污染代码血缘、日后分发即触雷；且工程上不划算（见 §4-D） |
| 6 | 把它的源码片段摘进 NASKB，NASKB 对外分发 | ❌ 违反 GPLv3 | NASKB 被传染，必须整体开源才合规 |
| 7 | 规避企业版授权校验 | ❌ 不要碰 | 且已确认企业模块不在开源仓库（独立闭源包 + license 动态加载），**无可解锁之物**——想绕也没有对象 |

**对你的场景的实际含义**：路线 A/B/C（实例整合、页面整合、fork 自用）全部落在 ✅ 区；
唯一要立规矩的是路线 D——**只允许「读它的代码学设计」，不允许「拷它的代码进仓库」**。
这条应写入编码纪律（可与 REQ-R6 并列）。另注意社区协议的**商标条款**：整合后自己的界面
与文档里不要使用 MaxKB 的 Logo/产品名做背书（描述性提及「基于 MaxKB 社区版」属正常范围）。

## 4. 五条整合路线逐一分析

### 路线 A：独立实例 + API 整合（主线推荐）

形态：MaxKB 社区版以 Docker 部署在你的 Linux 主机（REQ-R6-06 已预留），作为**独立的深度
分析引擎**运行；NASKB 通过适配器与其交互。

```
┌─────────────── NASKB（Windows 分析机 / v3 平台进程）───────────────┐
│  Web UI / MCP / CLI                                                │
│      │  统一契约 /api/search /api/ask（REQ-R3-04，前端不动）        │
│  ┌───▼────────────────────────────┐                                │
│  │ 检索后端链（config 开关切换）    │                                │
│  │ 本地引擎 ⇄ PG 引擎 ⇄ MaxKB 适配 │ ← 新增 Backend B（REQ-R5-03）   │
│  └───┬────────────────────────────┘                                │
│  export-maxkb / sync-maxkb（REQ-R5-02 内容管道）                    │
└──────┼──────────────────────────────┼──────────────────────────────┘
       │ 输出侧：应用 API Key          │ 输入侧：三选一（下表）
       ▼                              ▼
┌────────────── MaxKB 社区版（Linux 主机 Docker）────────────────────┐
│  应用对话 API（OpenAI 兼容，社区版）   知识库（标准库/研发库/项目库）│
│  工作流里可挂 NASKB 的 REST/MCP 工具   （REQ-R5-04 分级检索）        │
└────────────────────────────────────────────────────────────────────┘
```

**输出侧（问它）**：MaxKB 里为每类深析文档建应用 → 拿应用 API Key → NASKB 写 `MaxKBBackend`
实现既有 `/api/search` `/api/ask` 契约：`ask` 直通 OpenAI 兼容接口
（`POST /api/application/{id}/chat/completions`，`Authorization: Bearer application-xxx`，
社区版可用）并把命中来源映射回 NAS 路径；`search` 用检索测试接口或对应用做限定问答抽取
来源。**前端与上层调用方零改动**（这正是 ADR-20260816-2 当初留的口）。

**输入侧（喂它）**，按稳妥程度三选一，可递进：

| 方案 | 做法 | 评价 |
|---|---|---|
| ① 界面手动导入 | `export-maxkb` 从 `.naskb` 导出干净 Markdown/ZIP，人在 MaxKB 界面上传 | 零技术风险；缺点是要动手，适合起步期（几十~几百份文档完全够用） |
| ② 直调管理 REST API | 登录拿 token → 调 `/admin/api/*`（源码含文档导入接口，内置 Swagger `/admin/api-doc` 可自查全部端点），hash 对比增量同步（sync-maxkb） | 可全自动；社区已有成功实践；代价是非公开契约、升级可能变——适配层隔离 + Docker 锁版本 + 升级前跑契约测试 |
| ③ fork 封一层稳定管理 API | 见路线 C | ②的失败兜底 |

**分级检索闭环（REQ-R5-04）**：MaxKB 社区版工作流原生支持 **MCP 节点**——把 NASKB 的
MCP Server（14 个 `kb_*` 工具）或 REST `/api/search` 挂进工作流：精库（MaxKB 内的深析库）
优先、无果回落全库（NASKB）。MaxKB 出面对话，NASKB 做全库兜底，两边资产互相放大。

**优点**：法律最干净；两边各自升级互不牵连；界面/工作流/MCP 节点/嵌入浮窗白拿。
**代价**：多养一个系统（Docker + PostgreSQL + 升级跟进）；管理 API 方案有版本漂移维护成本；
**社区版 2 用户上限**——「多人共用」真出现时要么上专业版、要么换引擎（§5）。
**触发条件建议**：深析文档规模上百份、或出现「需要编排多个工具」「要现成问答界面给同事用」的
真实需求时启动。当前阶段不必急着上。

### 路线 B：页面级整合（赠品，不是主菜）

- MaxKB 应用生成的**嵌入脚本/iframe 浮窗**可直接嵌进 `serve` Web UI 或未来 v3 平台的页面，
  给「人」一个现成的深析问答入口，几乎零开发。
- 局限：只是 UI 拼接——没有程序化输入输出，不解决同步问题，样式/认证割裂（除非后续做 SSO）。
- **定位**：作为路线 A 的附带产出（反正实例已经跑起来了），不单独作为方案。

### 路线 C：Fork + 补丁（备胎，明确触发条件才启用）

做法：fork 社区版，基于源码里现成的 `/admin/api/*`（Swagger 可自查），封装一层**自己定义的
稳定管理 REST 契约**（建库/查重/上传/触发向量化/进度查询），其余保持原样跟踪上游。

- 法律：✅ 安全（不分发即无义务；一旦要对外提供，整体 GPLv3 开放）。
- 成本：每次跟上游升级都可能要重新对齐内部实现——这是长期税。适配层越薄税越轻。
- **定位**：路线 A 输入侧②被版本升级反复打断、且手动导入①确实撑不住时的 Plan B。
  不主动启动。

### 路线 D：组件级拆解（降级为「学习」，不建议搬代码）

§2.3 的结论直接决定这条路的性价比：**MaxKB 的可拆价值 ≈ 上游开源件 + 组装思路**。
搬它的自研代码进 NASKB（两套独立演进的代码库、GPLv3 血缘、升级断供，三重不划算）。
正确姿势：

1. **读代码学设计**（合法且免费）：分段策略默认值、段落/QA 双模式、检索测试界面的参数
   暴露方式、混合检索权重设计——记进设计笔记，用自己的代码实现；
2. **直接取上游**：需要同类能力时用 langchain/LlamaIndex、pgvector、pypdf 族/unstructured
   等原始库（MIT/Apache/BSD/PostgreSQL License），绕开 GPLv3——MaxKB 自己的解析层用的就是
   这些宽松许可的库加自研分段策略，说明「同类能力」在宽松许可生态里完全凑得齐；
3. 标准类复杂版式的解析标杆不在 MaxKB，在 RAGFlow 的 DeepDoc（Apache 2.0，可独立取用
   其 deepdoc 模块）——这是「拆组件」真正的正确目标。

### 路线 D'：自研 chunk 级检索增强（新识别的近道，建议优先）

上面四条路都在回答「怎么借助外面的系统」；这一条回答「能不能先把自家内核补齐」。

现状盘点：`.naskb/artifacts/` 里已经有 MinerU 产出的**结构化 Markdown**（标题层级天然对应
标准文档的章/节/条）；PG 多 NAS 向量库（R4，已实施）已有 resources/vectors 两表和完整的
指纹/状态机体系。缺的只是一段确定性代码：

```
chunk 增强（新增，确定性层）
  MinerU md → 按标题层级切分（H2/H3 为界，块间 10-15% 重叠，块带「第 X 章 > X.X.X」面包屑）
  → vectors 表扩 kind='chunk' 行（vector + summary_text=块文本 + full_text=所在节文本
    + parent_path 条款面包屑 + chunk_seq）
  → 检索时双层：chunk 命中 → 回溯 parent 取整节作 RAG 上下文 → 答案引用到「文件 + 条款」
```

要点与边界：

- **不动现有模型**：文件级检索（摘要索引）保持原样，chunk 行只挂在 PG 后端、只对标记为
  「深析」的目录启用——ADR-20260811-1「全文不进索引」的本意是防高频词稀释主题，chunk 文本
  是条款级语义单元，稀释风险远小于整文全文，但仍需新 ADR 明确豁免边界；
- 与「无 chunking」原则（REQ-R2-03）的关系：**修订而非推翻**——文件级不变，增加条款级第二层，
  且仅限显式圈定的深析范围；
- 成本：预计数百行确定性代码（md 解析 + 切分 + 入库 + 检索 SQL 扩展），无新依赖、无新系统、
  无许可证问题，完全复用 R4 的同步/指纹/回退链；
- 效果边界：解决「召回粒度」与「条款引用」，但不带来工作流编排、多用户、现成聊天界面——
  这些才是将来上 MaxKB/替代品的真实理由。

## 5. 替代品对比（如果不用 MaxKB，用什么）

调研结论（2026-08，GitHub/官方文档核对）：

| 项目 | 许可证 | 开源版 API | 部署重量 | 标准/规范类版式解析 | 备注 |
|---|---|---|---|---|---|
| **RAGFlow** | Apache-2.0（纯净） | 全量（建库/上传/解析/检索/对话 + OpenAI 兼容） | 重：≥4核/16GB（ES+MySQL+MinIO+Redis） | ★★★ DeepDoc（版面分析+表格结构识别+OCR） | 89k★ 活跃 |
| **Dify** | Apache-2.0＋附加（禁多租户 SaaS、保 LOGO） | Service API + 知识库 API 全量 | 中重：~10 容器 | ★★ | 153k★ |
| **FastGPT** | Apache-2.0＋附加（禁相似 SaaS、保 LOGO） | 知识库 OpenAPI + OpenAI 兼容 | 轻：3 容器（MongoDB+PG） | ★★（父分段/QA 分块可缓解） | 29k★ |
| AnythingLLM | MIT | 完整 REST + OpenAI 兼容 | 极轻：单容器 | ★ | 65k★ |
| QAnything | AGPL-3.0 | 有 | 中 | ★★ | **停更（2025-03 起）** |
| Open WebUI | BSD-3 变体＋品牌条款（>50 用户须保留品牌） | Files/Knowledge API | 极轻 | ★ | 150k★ |
| 自建 LlamaIndex+pgvector | 无限制 | 自定义 | 最轻 | 取决于 MinerU（我们强） | ＝路线 D' 的自然延伸 |

三个关键事实：

1. **「API 要企业版」是 MaxKB 特有问题，不是品类问题**——上表所有系统的开源版 API 全量免费；
2. **标准/规范类的解析质量天花板是 RAGFlow DeepDoc**，且它是纯 Apache 2.0，deepdoc 模块
   可单独抽用（这才是值得「拆」的组件）；代价是 16GB 内存门槛，你的 Linux 主机若富余可承受；
3. 我们已有的 MinerU 前置解析可以把除 RAGFlow 外所有方案的版式短板拉平——解析层本来就是
   NASKB 的强项，选型时不应为此付双份钱。

**替代品与路线的关系**：路线 A 的架构图中「MaxKB 适配器」的位置，换成 RAGFlow/FastGPT 适配器
完全同构（它们甚至更省事：管理 API 官方公开、无需碰内部接口）。因此**路线 A 是「深度引擎可插拔」
的架构决策，不是对 MaxKB 的单方面承诺**；MaxKB 只是候选之一，其独特优势仅在：中文界面成熟、
你已经调研过、界面操作体验好（个人使用友好）。

## 6. 推荐决策

### 6.1 分阶段路线（与「轻量起步、按需升级」原则一致）

| 阶段 | 动作 | 触发条件 | 对应需求 |
|---|---|---|---|
| **现在** | 路线 D'：chunk 级检索增强（PG 后端、深析目录圈定、条款面包屑、parent-child 上下文） | 标准/规范类文档的条款级问答已是现实痛点 | 新增 REQ-R5-06 + 新 ADR（修订 REQ-R2-03 边界） |
| **现在（顺带）** | `export-maxkb` 干净 Markdown 导出命令 | 无论最终选谁，干净文本管道都是公共资产 | 升格 REQ-R5-02 前半段 |
| **将来** | 路线 A：深度引擎独立实例（届时在 MaxKB / RAGFlow / FastGPT 中按当时状态二次选型），Backend B 同契约接入；页面嵌入作附带 | 深析文档上百份 / 多人共用 / 需要工作流编排 | REQ-R5-01/03/04 维持 |
| **备胎** | 路线 C：fork 补管理 API | 仅当所选引擎的管理 API 长期缺失且手动导入不可忍受 | 新增 REQ-R5-07（条件触发） |
| **不做** | 路线 D 搬代码；规避企业授权 | —— | 写入编码纪律 |

### 6.2 一句话回答原问题

> 「从内部 API 层面或页面层面整合」可行吗？

可行且合法：**页面层面**是路线 B（嵌入浮窗，赠品）；**API 层面**分两半——对话 API 社区版
本来就开放（直接用），文档管理 API 的代码就开在你部署的实例里（直调可行、自担版本风险；
官方收费的是平台级「开放 API」产品化包装），并有「手动导入 / 直调管理 API / fork 封装」
三级递进方案。但**建议先走 D'**：你要的能力八成是「条款级精准问答」，这在自家 PG 内核上加
chunk 层就能拿到，还不用多养一个系统；MaxKB（或 RAGFlow）留给「工作流/多用户/现成界面」
需求真正出现的那一天，且到时候选型不必锁定 MaxKB。

## 8. 风险清单

| 风险 | 影响 | 对策 |
|---|---|---|
| 内部 REST API 随版本漂移 | sync-maxkb 断裂 | 适配层隔离 + Docker 锁版本 + 升级前跑契约测试；手动导入永远可用作兜底 |
| MaxKB 社区版商业化收缩（开源功能进一步阉割） | 被迫迁移 | 内容管道双向干净（.naskb 是事实源，MaxKB 库随时可重建）；选型时保留 RAGFlow/FastGPT 替代选项 |
| chunk 层引入后检索质量反而下降（条款碎片化） | 违背初衷 | 仅对深析圈定目录启用；块带面包屑与重叠；上线前用固定问题集做前后对比评测 |
| RAGFlow 类重型引擎吃满 Linux 主机内存 | 拖垮同机服务 | 触发条件评估时先量内存余量；不够则退 FastGPT（3 容器）或继续用 D' 自研 |
| GPL 血缘污染（有人顺手抄代码） | 分发即违规 | §7-7 编码纪律 + code review 关注点 |
| 社区版上限撞墙（50 知识库/5 应用/**2 用户**） | 扩展被迫中断或临时买专业版 | 在上限内规划应用数量；撞墙时按当时价格重估专业版 vs 换引擎（架构已可插拔，切换成本低） |
