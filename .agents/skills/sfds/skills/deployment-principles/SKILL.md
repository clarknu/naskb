# deployment-principles（部署总原则）

**性质：原则/评审资产（无步骤流程）**，由 `release-management`（发布门禁）与 `review`（校核维度）引用，并可**按触发词独立触发**。本技能把「环境拓扑规范 + 通用中间件资源放置 + 部署总原则」统一为一条可判定的**部署合规评审**。

## 部署总原则（总纲）

1. **最小资源足迹（能少开就少开）**——能用共享/既有实例就不新建；能少起服务就少起；关闭即释放，资源不为"以防万一"常驻。
2. **复用共享基础设施（共用数据库）**——数据库/中间件优先**共享独立实例**，跨环境/系统**按库名/用户逻辑隔离**（同库主机、不同库名，最多分属不同用户），**不引入主机级物理隔离**。
3. **少第三方组件（尽可能少用三方组件）**——优先宿主机原生、自建可控或统一管理的独立实例（RDS/云 Redis/统一容器）；业务 compose 不自建公共中间件。
4. **三环境同构**——研发/预发/生产结构一致，仅局部分别配置、整体架构不超既定范围。
5. **机密入加密库、引用不写真值**——凭证走 `<CREDENTIAL:proj/key>`（见 `credential-management`）；部署文档与脚本不落明文。
6. **配置单一真相源 + 记录留痕**——部署配置由项目侧过程资产（`deployment-config-guide.md`）圈定；坑与注意、下次部署步骤随项目记录；改动同步更新文档与资产库。
7. **网络分层访问（宿主机分层，§三）**——公共中间件经**宿主端口**接入；**一个项目一个 Docker 网络**（跨环境共享、服务名互访）；对外**只经 Nginx 层反向代理 + 域名映射**。内网不出公网；对外一律走 Nginx/域名映射（或隧道兜底，见 release-management §八 #17）。

> 总原则的关系：原则 1/3 = 资源放置（§二）；2/4 = 环境拓扑与逻辑隔离（§一）；5 = 密钥边界（`credential-management`）；6 = 过程资产治理（`release-management` 定义）；**7 = 网络访问拓扑（§三）**。本技能只承载「原则/评审」，不承载流程与工具。

## 一、环境拓扑规范（每个项目的环境长什么样才算合规）

1. **线上环境结构一致、不超既定范围**：每个项目的线上环境配置一致，不会超出既定范围；可对不同部分做**局部单独配置**，但**整体架构保持一致**。
2. **环境不是随意堆积**：新增/删除环境、或改动三环境拓扑，必须走本规范与 `release-management` 评审，禁止凭手感随手加层/改边界。
3. **本地开发环境（Local Dev）**：运行在**开发工作机**上，提供相对完整的环境，通常能**跑通所有功能**；涉及第三方连接（如外网）时通过 **Mock 或网络转发**等方式绕过。**核心原则：所有自建构建、引入的第三方中间件及业务系统，原则上不出子网。** 数据库等组件也遵循此原则——可部署在本机，或子网内其它主机（§二 界定为宿主机原生/统一独立实例）。
4. **预发布环境（Pre-release）**：接近**真实线上**环境。**第三方服务配置与发布环境保持一致**：例如发布环境若连某台线上 RDS，**预发环境也连接同一台库主机，仅库名不同**（预发库 vs 正式库）——**逻辑隔离**。**自建引入的第三方组件 / 中间件，尽可能使用同一台主机**，只要满足**数据隔离**要求即可。若第三方组件**轻量化且属于系统一部分**，则预发环境需**独立部署一套**，与主系统**部署方式一致**。
5. **正式环境（Prod）**：配置方式、连接关系按架构文档圈定；密钥 / 域名独立。
6. **数据库隔离元规则（全员适用）**：数据库一般**不需要主机级物理隔离**；跨环境（本地 / 预发 / 正式）一律按**逻辑隔离**处理——同库主机、不同库名（最多另分用户）。是否用独立实例/托管实例（RDS 等）由「资源放置」维度（§二）决定，与本条**正交**。

## 二、通用中间件资源放置（实例怎么放）

1. **公共服务外置**：数据库 / Redis / 消息队列 / 对象存储 / 向量库等，用宿主机原生安装或统一管理的**独立实例**（RDS / 云 Redis / 统一编排容器）；**避免每个业务容器各自启动公共服务**。
2. **业务 compose 只声明自身容器**：平台应用、OpenProject、Dify 等业务组件的 compose 不得自建 PG/Redis；若某系统内多个服务进程混用，会导致冲突。
3. **compose 自带公共服务定义要移除/不实例化**：如 Dify 默认 compose 自带的 `redis` / `postgres` 服务——不实例化或删除定义与相关 `depends_on`。
4. **容器访问宿主服务**：`extra_hosts: host.docker.internal:host-gateway`（Linux 宿主）或内网 IP + 白名单。
5. **三环境同构**：研发 / 预发 / 生产保持同一结构，不因环境不同各自另起公共服务。
6. **多系统共享独立实例**：同一独立 PG/Redis 可被多个系统复用，但**每系统独立库/用户/密码**（如 `platform` / `openproject` / `dify` 各一库一用户），避免数据串扰。
7. **独立实例凭据集中管理**：独立实例的凭据（`.credentials/`/加密库，见 `credential-management`）集中管理，不入库、不进镜像。

## 三、网络访问拓扑（宿主机分层）

> **用户裁决（2026-08-30）**：线上主机网络访问按"三层"组织——公共中间件经宿主端口、项目内一网通、对外只经 Nginx/域名映射。这是**内网不出公网**的部署网络约束。

1. **公共中间件经宿主端口接入（内网统一入口）**——公共中间件（如 Redis、PG、消息队列等）接入一套网络并在**宿主机 Host** 上暴露访问端口；需要这些中间件的服务一律**通过宿主机端口**访问（内网，不出公网）。
   - **Redis** 若为**原生安装** → 用**原生 Host 绑定**（如 `redis-server` 绑 `0.0.0.0:6379` + `requirepass`）。
   - **PG** 若在 **Docker 网络**里 → 将其端口**映射到 Host**（如 `-p <hostPort>:5432`、宿主监听）供其它服务经宿主访问。
   - 公共中间件默认**不直接进业务 Docker 网络**，而是经宿主端口作为**统一入口**（便于集中管理/鉴权/审计）。

2. **一个项目一个 Docker 网络（跨环境共享、服务名互访）**——每个**独立项目/产品**（如"智元的咨询"、"智元的智能床"），其**所有环境**（Production/Beta/Alpha 等）若归属同一项目，则在**同一宿主机**上用**同一个 Docker 网络**。
   - 同一项目内各环境/服务互相用 **Docker 网络服务名**访问（内网直达，不经公网、不经宿主端口）。
   - 仅在用到**公共资源**（PG、Redis）时经**宿主端口**访问（仍内网）。
   - 各服务把**对外端口映射到宿主**，但该映射**仅宿主机内部可访问**，不直接暴露公网。

3. **Nginx 层统一对外（域名映射反向代理）**——在**所有 Docker 网络与宿主网络之外**架一层 **Nginx**（反向代理）。
   - 对外一律通过 **域名映射** 经 Nginx 暴露；不同产品/环境对内网用**不同端口**，但**对外网都必须经宿主机 Nginx 反向代理**才能访问。
   - 需要从外网访问的（如公共中间件管理、某环境 UI）都经 Nginx 按域名/路径代理到对应内网端口。
   - **直接命中公网的只有 Nginx 层**（或隧道兜底，见 release-management §八 #17）；业务容器/宿主端口不直接暴露公网。
   - 举例：想经外网访问公共 PG → 通过 Nginx 暴露访问方式，而非直连宿主端口。

## 四、评审检查清单

- [ ] **线上结构**：线上环境结构是否一致、不超既定范围（仅局部分别配置），整体架构是否符合架构文档？
- [ ] **本地开发**：自建构建 / 第三方中间件 / 业务系统是否**不出子网**？外网连接是否以 Mock / 网络转发绕过？
- [ ] **预发布**：第三方服务配置是否与线上**一致**（同库主机、仅库名不同=逻辑隔离）？自建组件是否尽量复用同一主机（满足数据隔离）？轻量系统组件是否独立部署一套、与主系统同构？
- [ ] **数据库**：是否按**逻辑隔离**（同一库主机、仅库名不同，最多分属不同用户）而非主机级物理隔离？实例是否为宿主机原生/统一管理的独立实例（无业务 compose 自建）？
- [ ] **通用中间件**：业务容器内是否有自建 PG/内嵌库？→ 应指向独立 RDS/实例；是否有 compose 自带 Redis 容器？→ 应指向宿主/云 Redis；队列/缓存/对象存储/向量库同理外置。
- [ ] **三环境同构**：dev / pre / prod 结构是否一致？
- [ ] **独立部署界定**：是否明确区分「独立部署」与「不独立部署」的配置？
- [ ] **文档**：本地 / 预发 / 正式三套环境的**组件、连接方式、部署方法**是否有文档记录？
- [ ] **配置发布**：是否依赖架构文档圈定的整体架构？
- [ ] **机密**：是否存入 Credential Vault（`credential-management`）并在部署时注入，未硬编码进代码/镜像/可执行？
- [ ] **凭据**：独立实例凭据是否集中管理（不入库、不进镜像）？
- [ ] **网络-公共中间件**：公共中间件（Redis/PG/MQ 等）是否经**宿主端口**接入（内网统一入口），而非散落各业务网络？Redis 原生是否走原生 Host 绑定、PG 容器是否映射到 Host？
- [ ] **网络-一项目一网**：归属同一项目的各环境是否在**同一宿主机、同一 Docker 网络**？项目内服务互访是否用**服务名**（不经公网/宿主端口）？仅公共资源经宿主端口？
- [ ] **网络-对外统一入口**：对外暴露是否**只经 Nginx 反向代理 + 域名映射**？业务容器/宿主端口是否**不直接暴露公网**？（或仅隧道兜底）

## 五、正例 / 反例

| 场景 | 反例（违规） | 正例（遵循） |
|------|------------|------------|
| 数据库 | 预发另起一台全新 RDS（物理隔离过度），与线上不一致 | 预发**复用线上同一台库主机，仅库名不同**（逻辑隔离），与线上配置一致 |
| 第三方中间件 | 本地开发直连公网第三方服务、无 mock / 网络转发 | 本地在子网内以 Mock / 网络转发绕过，中间件不出子网 |
| 轻量系统组件 | 预发与线上混用同一实例，无独立一套、无数据隔离 | 轻量系统组件在预发**独立部署一套**，与主系统同构 |
| Dify 部署 | compose 里跑自带 `redis:6-alpine` + `postgres` | 移除自带服务，`REDIS_HOST` 指向宿主 Redis，DB 指向独立 PG |
| 平台后端 | 容器内嵌 sqlite/pg 数据 | `DATABASE_URL` 指向统一 PG（RDS 或独立实例） |
| 多系统同机 | OpenProject 内嵌 PG + 平台内嵌 PG 并存 | 共享独立 PG 实例（每系统一库一用户） |
| 配置管理 | 部署配置散落、无统一架构文档；机密硬编码进代码/镜像 | 三环境配置随架构文档圈定；机密存 Credential Vault，部署时注入 |
| 网络-公共中间件 | 每个业务容器各自起 Redis/PG，服务各处直连 | 公共 Redis/PG 统一**宿主端口**接入；业务经宿主端口访问（内网，不出公网） |
| 网络-一项目一网 | 同项目各环境/服务用不同 Docker 网络，互访要走宿主端口/公网 IP | 同项目共用**同一 Docker 网络**，服务名直连；仅公共资源经宿主端口 |
| 网络-对外 | 业务容器/宿主端口直接暴露公网 | 对外**只经 Nginx 域名映射反代**；Nginx（或隧道兜底）是唯一公网入口 |

## 参考案例 / 关联

- **原则来源与互补**：原则 1/3/6 = 资源放置（原 `infra-service-isolation`）；原则 2/4/6（拓扑/隔离）= 环境拓扑（原 `deployment-environment-model`）；原则 5 = `credential-management`；原则 6（过程资产）= `release-management`；原则 7（网络分层）= 2026-08-30 需求方确立的**宿主网络分层**约束（见 §三）。
- **网络分层与其它原则的关系**：§三 原则 1（公共中间件宿主端口）落实「少第三方组件/宿主原生独立实例」（原则 3）+「复用共享基础设施」（原则 2）；原则 2（一项目一网）落实「环境拓扑/内网隔离」（§一 本地不出子网）；原则 3（Nginx 统一对外）落实 release-management §八 #17（默认直接域名映射、对外只经 Nginx/隧道兜底）。

- **zy-iot-ai**（智能床云端，线上案例）：ECS 生产用**内网 RDS**（`10.0.0.153:5432`）独立实例，nginx 反代 + systemd 守护，无容器内自建中间件。
