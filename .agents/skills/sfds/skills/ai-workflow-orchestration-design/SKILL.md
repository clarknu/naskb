# AI 工作流编排设计方法论（团队级）

> **定位**：团队/企业级方法论——既非普适技术知识，也非单个项目的可变策略。
> **适用**：所有采用"编排层 + 执行层"架构的项目（Dify、n8n 等工作流平台）。
> **分工**：本 Skill 只写"怎么做"（方法论，跨项目复用）；"做什么"（具体流清单、节点参数、权限矩阵、业务规则）在各项目设计文档中。
> **维护**：随项目逐个迭代更新（项目级工作副本 → 成熟后升全局 `~/.agents/skills/` 供下一项目使用）。

---

## 一、使用方式

1. **设计前**：先读本 Skill 六项原则（P1-P6），再读项目设计文档（该项目的流清单/节点/权限）。
2. **设计时**：产出每条流时按 P1-P6 逐条自检（见"输出要求"）。
3. **复查时**：见 §五 校验与集成闭环（review 可选 D13 维度 + iterate 前置自检；仅项目含 AI 工作流架构资产时启用）。

---

## 二、六项原则

### P1 分层哲学：编排层管流程与对话，执行层管身份、权限与数据

- **编排层**（Dify 等）：流程编排、对话管理、LLM 节点、工具调用节点、定时触发。
- **执行层**（平台工具 API / 后端服务）：一切数据读写、身份代理、权限门、审计。
- 编排层**不持有任何用户凭据**；工具调用必须经执行层——携带**用户标识**（如 userid）、**不携带凭据**。
- **判定**：任何需要"读/写业务数据"的节点必须落在执行层；编排层只做流程、对话与展示。

### P2 确定性优先

- **固定/常规指令**：优先走规则（模板 / 关键词 / 固定工作流），零或低 LLM 成本。
- **模糊指令**：才走 LLM 分类；LLM 只负责"理解与生成"，**不负责数据操作**。
- 工具执行统一经执行层（原子、鉴权、审计），编排层不做直接数据变更。

### P3 状态持久化

- 业务状态（确认清单、会话、提醒、批次等）**持久化到数据库**；编排层变量仅作**临时上下文**。
- **不信任编排层内存态**；中断 / 恢复以数据库状态为准。

### P4 节点判定：内置节点优先，自定义节点只做纯逻辑

- **优先使用平台内置节点**（LLM、条件分支、迭代、定时触发、工具调用、模板转换、参数提取等）。
- **自定义节点**仅当"项目特有、无内置等价物"时创建；且必须是**纯函数 / 规则**：
  - 不做数据操作（数据经执行层工具获取）；
  - 不持有凭据；
  - 可测试、可解释。
- **判定步骤**：①内置能否满足？→ ②能否用"工具调用 + 内置组合"满足？→ ③才考虑自定义节点。

### P5 走向判定规范

- 每个分支必须有**明确的判定口径**（条件 / 阈值）与**兜底路径**。
- 兜底模板：低置信 → **澄清追问**；未知 → 转**通用 LLM 聊天**并记录；失败 → 回显 / 重试。
- **高危操作**（删除 / 批量 / 不可逆）在流程中显式设置**二次确认**。

### P6 会话隔离

- 按**用户 / 群 / 会话**隔离上下文，防串扰与超窗。
- 会话映射**持久化**（用户 / 群 ↔ 编排会话），可恢复。

#### P6.1 会话隔离闭环（持久化细则）

| 环节 | 规则 |
|------|------|
| 存哪 | 会话映射+业务状态一律落**执行层数据库**（或项目约定的持久化存储），编排层变量仅临时上下文 |
| 何时建立 | 会话首次触发时写入：`{用户/群标识, 编排会话 id, 路由上下文, 时间戳}` |
| 恢复 | 中断/重开后按持久化映射重建会话；无映射则按"新会话"处理并记录（防串扰） |
| 失效与清理 | 超窗/结束事件 → 标记失效并归档；清理不得删除审计所需历史 |
| 校验 | 断点恢复后必须校验"上下文=该会话该用户"，防跨会话注入（列入 §五 校验清单） |

## 三、输出要求（设计任何工作流时的产出物）

每条流必须包含：

| 要素 | 要求 | 对应原则 |
|------|------|----------|
| 触发方式 | 消息 / 定时 / 事件 / 指令 | — |
| 节点链 | 节点名 / 类型（内置/自定义/工具）/ 职能 / 走向判定 | P4/P5 |
| 自定义节点理由 | 每个自定义节点必须说明"为什么无内置等价物" | P4 |
| 操作者身份与权限 | 每条流标注操作者、权限门、高危二次确认 | P1/P5 |
| 数据与状态 | 数据经执行层、状态落库 | P1/P3 |

> 参考模板：项目实现架构文档（如 `docs/implementation-architecture.md` §3 的流设计表）。

### 产出物落位（与架构资产体系平级）

AI 工作流架构是**架构设计的一种**（与后端架构、前端架构、数据库架构同等待遇）：

- 设计产物 → 项目 `design/` 下统一架构资产区（如 `design/08-ai-workflow/{flow-slug}.js`，格式与其余架构资产一致：**JS 数据 + viewer 渲染，可 diff、可回滚**；项目无此区时按 development-standard 初始化流程约定创建）。
- 每批流清单/节点参数/权限矩阵 → 项目设计文档（"做什么"留在文档，本 Skill 只写"怎么做"）。
- 变更走统一纪律：改流设计必须连带实现/验证同步更新（与其它架构资产同规则）。

## 四、与项目设计文档的分工（三问自检）

设计任何节点 / 分支前，先问：

1. **这是"通用知识"还是"团队方法论"？** 通用知识（API 长什么样）→ 查 references / 文档，不进 Skill。
2. **这是"项目策略"还是"团队方法论"？** 项目策略（本项目用什么交互、什么权限矩阵）→ 写项目设计文档，AI 按文档走。
3. **这是"团队方法论"吗？** 团队独有的设计原则（本 Skill 六项）→ 沉淀到 Skill，跨项目复用。

> 团队级 Skill 的迭代方式：**跟项目走**——在一个项目里使用并迭代，项目完成后成熟部分升全局供下一项目复用。

## 五、校验与集成闭环（P1-P6 自检清单 + 接入点）

### 5.1 设计自检（每条流产出时逐项勾选）

| # | 检查 | 原则 |
|---|------|------|
| 1 | 数据读写/身份/权限/审计是否全部落在执行层？编排层是否零凭据？ | P1 |
| 2 | 固定路径是否走规则（模板/固定流）而非 LLM？LLM 是否只做理解与生成？ | P2 |
| 3 | 业务状态是否落库而非编排层内存态？ | P3 |
| 4 | 节点是否"内置→组合→自定义"三步判定？自定义是否纯函数且说明理由？ | P4 |
| 5 | 每个分支是否有明确判定口径+兜底路径？高危是否二次确认？ | P5 |
| 6 | 会话是否按 用户/群/会话 隔离？映射是否持久化且断点恢复后校验归属（P6.1 全项）？ | P6 |

自检结论（每项 ✓/✗ + 说明）随流设计文档归档。

### 5.2 实施验证（落地闭环）

- 每条流至少 **1 条端到端验证用例**（确定性路径断言）；有兜底分支的流另加兜底路径用例。
- 用例落位：项目测试体系（TDD/平台 e2e），执行时机 = 该流交付及发布前（对应 release 门禁）。
- 流的触发/权限/状态变更全部可被自动化验证用例覆盖（无手测豁免）。

### 5.3 复查接入（接线闭环）

- **review**：项目含 AI 工作流架构资产时启用可选维度 **D13（AI 工作流合规）**——按 5.1 清单逐项核对（对接 dispatch 表）。
- **iterate**：改动涉及工作流（流设计/节点/走向/会话映射）时，修复/迭代按 P1-P6 清单自检并落测试（同 5.2）。
- **状态**：本项目工作流资产进 pipeline-state（与其它架构资产同登记），发布前复查含 D13。

> 修订记录：2026-08-23（CASE：AUD-1 解耦→改为接线）——本 Skill 原声明"review/iterate 按 P1-P6 校验"但无接线维度，现补全为可执行闭环（D13 可选维度 + 自检清单 + E2E 用例 + 状态登记）。
