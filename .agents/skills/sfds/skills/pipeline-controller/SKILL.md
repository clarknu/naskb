# pipeline-controller

目标：把用户从「人肉调度器」解放出来。用户只做三件事——**抛问题**、**批方案**、**答确认**。其余（分析、排队、保鲜、执行、测试、修复、commit、出队）自动。

本 skill 是**全局行为说明书 + 可实例化的护栏**。它本身不含任何项目状态；每个项目通过一份 `.pipeline/PIPELINE.md`（队列状态+事件日志）+ 一套脚本（锁/新鲜度/验证）落地——那些是数据与硬约束，不是本 skill。

## 默认激活与分层（2026-08-29 新增，强制，CASE-015/016 回灌）

> **病根**：单次会话内联跑的 iterate 工作，一旦 DSH 后台崩溃 / session 丢失 / 后台进程死掉，过程与结论都会丢；而本 skill 因「默认不激活」无法兜底。用户要求**开发类工作默认走流水线**，让"要做的事 + 当前状态 + 过程信息"都落盘在项目里、可 git 追踪、崩溃后可捡回。（需求方 2026-08-30 确认采纳：把「默认不激活」改为「开发类默认激活」。）

**两条规则：**

1. **开发类工作默认进流水线模式。** 凡触发 `iterate` 关键词的工作（重构 / 需求 / bug 修复 / 迭代 / 联调修正等），**默认登记为一条 `T-xxx` 任务**进入 `.pipeline/PIPELINE.md` 队列，走 分析 → 待审批 → 新鲜度门 → 后台持锁执行 → 验证 → 1 任务 1 commit，并落「过程留痕」（见下节）。**不再默认「单次会话内联跑一遍」。** 唯一例外：用户显式声明「一次性 / 直接改 / 不用管线」（见投喂模式开关）时才内联；无明确声明时不猜、按默认流水线走。
2. **分层（职责分离，能力叠加不重复）：**
   - `pipeline-controller` = **外壳**：队列 / 全局写锁 / 后台执行 / 主对话零阻塞 / 跨会话恢复 / 过程留痕。
   - `iterate` = **内容引擎**：§8.x 级联计划（FA / FC + C1 / C2 / C3）作为该 T-xxx 任务的执行内容，跑在流水线任务内部。
   - 即：**外壳负责「怎样可靠地串行执行并落盘」，内容负责「改什么、改多大、怎么级联」。** 两层叠加，不互相替代。

## 最高铁律：主对话零阻塞（CASE-008 / R1）

> **本 skill 的首要设计目标是：用户在任何时刻都能继续说话。**

1. 编排器（主对话线程）**永不内联执行任何任务**——分析、执行、验证、修复一律派发。
2. 执行/验证类工作必须派发给**后台子代理**；派发动作完成后**立即结束当前回合**，向用户回执：「T-xxx 已在后台执行（写锁：占用/空闲），队列空闲，请继续下指令」。
3. 判定标准与任务大小无关：凡是不能在一个即时动作内完成的操作（跑构建、跑测试、部署、批量修改），都不允许占据主对话回合。
4. 违反本铁律的具体症状（自查）：回合内出现"正在等待测试完成/部署进行中"之类的持续等待——出现即违规，应改为后台派发。

## 执行者模型（三分）

| 角色 | 载体 | 并行性 | 上下文 |
|------|------|--------|--------|
| 分析 | 只读子代理 | 无限并行 | 独立只读上下文 |
| **执行+验证+修复** | **后台子代理** | 全仓库共用一把写锁，串行 | 子代理内部获取 `lock`；主对话不持有任何执行过程 |
| 编排器（主对话） | 主线程 | 永远可用 | 只保留「活跃任务面板 + 各任务方案摘要 + PIPELINE.md 状态行」 |

## 前后台通信协议

后台子代理必须在关键节点产出结构化事件；编排器负责把事件推到前台。

### 事件类型

| 事件 | 含义 | 前台呈现 |
|------|------|----------|
| `PROGRESS` | 阶段边界到达（构建完/部署完/测试绿/门禁过/commit 完成） | 时间线播报：`T-001 ▸ 构建✓ ▸ 部署中…` |
| `NEED-INPUT` | 需要用户确认（含问题、选项、影响面） | **置顶提示**，标注持锁状态 |
| `DONE` | 任务完成（commit hash + 验证结果） | 完成回执，出队下一个 |
| `BLOCKED` | 修复 3 轮仍失败 / 熔断触发 | 受阻说明 + 需要用户做什么 |
| `FAILED` | 后台代理异常终止 | 失败原因 + 重试指引 |

### 播报规则

1. **进度是推给用户的，不是用户问来的**：编排器在每个回合开始时，先播报自上次交互以来累积的未读事件（时间线形式，一段话以内）。
2. **确认双通道**：后台发出 `NEED-INPUT` → 编排器置顶提示；用户用自然语言直接作答（如"可以放行"/"选方案 B"）→ 编排器识别为对该任务的答复，经消息通道转发给后台代理 → 后台**不中断、不重启**继续执行。
3. **阻塞型确认**（生产放行、不可逆操作）期间写锁保持，前台显著标注「⚠️ 队列被 T-xxx 的确认卡住」；用户可指令「先取消 T-xxx」→ 回滚其变更、释放锁、任务转受阻。
4. 执行期间用户的新话语照常按「会话识别」分流（新问题→并行分析；决策→更新队列），**绝不因"正在执行"而拒收或延后处理**。

## 任务语义：同步请求 ≠ 同步等待（CASE-008 / R4）

- 「启动发布」「跑一轮全量测试」这类指令的语义是**异步启动**：立即派发、立即交还控制权，而不是站在原地等它跑完。
- 长闭环（release 等）拆为多段 PIPELINE 任务（如：构建打包 / 部署 beta / 冒烟验证 / 待放行），每段独立过新鲜度门、独立 commit、独立事件流。
- 用户若明确要求同步等待（"等我确认了再继续"），按普通停等处理，但每阶段边界仍须回执。

## 核心状态机

```
新问题 ─▶ 分析中(任意并行) ─▶ 待审批 ─▶ 排队(写锁 FIFO)
                                        │ 锁空闲
                                        ▼
                                新鲜度门(增量复核)
                                 │ 有效         │ 失效
                                 ▼              ▼
                        执行中(后台子代理·全局唯一)  打回待审批+原因
                            │            │
                 PROGRESS(节点回推)   NEED-INPUT(置顶确认→答复转发)
                            ▼
                        自动验证 ──失败──▶ 带报错自动修复(≤3轮)
                            ▼ 通过                 │ 仍失败
                       完成✓ 出队下一个        blocked，通知人
```

## 关键规则（强制执行）

0. **零阻塞优先**：与本文件任何条款冲突时，以「主对话零阻塞」为准。
1. **读写分离**：分析类任务只读代码，可并行任意数量。改代码任务在全仓库共用一把写锁，任何时刻最多一个任务处于 执行/测试/修复。锁用 `<项目>/.pipeline/lock` 文件记录（内容 = 当前任务 id + 时间戳）。**写锁由后台子代理获取与释放，主对话永不持有。**
2. **出队前必须过新鲜度门**：先跑 `freshness.ps1 -Baseline <批准时commit> -Touches <影响面> -Project <项目>`。返回 `UNCHANGED` → 直接执行；返回 `CHANGED` → 把「原方案 + git diff 增量」交给子代理做增量复核，结论三选一：照旧执行 / 微调后执行 / 失效打回（附原因，转待审批，并通知用户）。执行期插入的新意见在队列中自然排队，由本机制适应前 N 轮改动。
3. **执行后必须验证**（在后台子代理内进行）：有测试模块 → 跑测试，失败带报错自动修复，最多 3 轮，仍失败 → BLOCKED 并通知用户；无测试模块 → 至少跑编译/类型检查/构建，通过后任务停在「待人工验证」，等人点头。
4. **提交纪律**：一任务一 commit，message 带 `[T-xxx]` 前缀；每步可回滚。
5. **熔断**：连续 2 个任务 BLOCKED → 暂停出队，通知用户。
6. **上线**：默认不含 deploy。需要时作为独立流水线阶段拆段执行，生产环境停在「待放行」（NEED-INPUT 事件）；「启动发布」默认异步语义（见上节）。
7. **粒度**：一个任务 = 一个可独立验证的闭环；过大就拆。

## 投喂模式开关（feeding-mode switch，2026-08-26 新回灌）

> **病根复盘**：用户说「等我设计完再执行」只是**执行开关**，但若在此之前就建了目标（goal）并武装，目标会自动逐轮空转——多轮投喂阶段尤其致命。本开关把「**模式开关**（是否自动推进）在任务开头锁定」与「**执行开关**（设计完才动手）在任务末尾触发」两个层次彻底分开。

**两种模式，用一个开头提示词触发，由编排器识别锁定：**

| 你的话术（任一即可） | 判定 | 行为 |
|---|---|---|
| 「一次性给你 / 这是一次性需求 / 一口气讲完 / 不用等我」 | **模式 A · 一次性**（默认） | 按常规流程：需长任务则 `create_goal` + 正常逐轮推进 |
| 「多轮投喂 / 逐条给 / 分几步告诉你 / 先说第一条 / 等我说『设计完成』再执行 / 我会逐个告诉你」 | **模式 B · 多轮** | **不建目标、不自动推进**，只逐条收 + 当场对齐 |

**完成开关（模式 B 的关闭词，任一即可）：**
- 「设计完成」「投喂完成」「讲完了」「就这样定了」
- 触发行为：**这一刻才 `create_goal`**，正式进入 分析→待审批→新鲜度门→后台执行→验证 流水线。

**兜底（防歧义）**：一条消息既无 A 也无 B 信号，但内容像 "Part 1 / 还有后续" 或正处多轮语境 → 问一句轻量确认（一次性 / 还有后续？），不猜、不空转。

**核心原则（治本）**：
> **模式 B 中，只要没收到的关闭词，编排器绝不 `create_goal`** → 从根上杜绝「自动逐轮空转」。用户忘了完成词，顶多是一直收、不执行，**绝不越界跑**。

## 目标自动续跑 × 审批门：零空转铁律（2026-08-27 回灌，强制）

> **病根复盘**：编排器建了带自动续跑的目标（`create_goal`），分析完提交「待审批/NEED-INPUT」后，本应「停着等用户」，但因为目标**自动续跑**，每个回合都重新拉起编排器重复播报同一种话（如「等待你批准」）——形成可见空转。用户可观察症状：**连续多个回合重复同一句「等待用户批准/确认」= 违规空转**。

**规则（强制执行，高于本文件其余条款冲突时以本条为准）：**

1. **需要用户决策的门 = 立即停点**：任何「待审批 / NEED-INPUT / 生产放行 / 请用户确认」关卡出现时，编排器在该 turn 内**立即把当前目标的自动续跑置停**（disarmed：走 blocked/pause 语义），绝不让它在等待期间继续自动推进。
2. **每门只提醒一次**：该门只向用户**播报一次**（方案摘要 + 待批事项 + 基线），之后完全**静默**，直到用户给出新的明确指令（批准 / 改方案 / 暂停 / 下一条需求）才恢复动作；用户未开口前**不生成任何新的自动回合**。
3. **只由用户显式指令驱动恢复**：目标仅由用户明确的指令恢复（或用户明确授权的全自动闭环，如 release 全自动）；任何「正在执行 / 等待批复」状态都不构成自动续跑的理由。
4. **单任务 + 审批门 优先不用自动续跑目标**：这类流程优先直接用 `.pipeline/PIPELINE.md` 的「待审批 / 排队」位 + 后台执行子代理，把审批门当作**自然停点**，不依赖 `create_goal`；确需目标时，提交该门的**同一 turn 内**就把目标置停。
5. **自查信号（违规判定）**：一旦出现「≥2 个回合在重复同一句等待/确认类播报」→ 立即收口为**一次播报 + 置停**，并向用户说明（不辩解）。

## 任务编号位宽约定（2026-08-26 新回灌）

> 澄清一个易混淆点：目标系统 ID（`goal-<uuid>`）是**随机哈希、永不绝版**，与流水线里人/编排器维护的**任务短标签 `T-xxx`**完全无关。本约定只管 **`T-xxx` 短标签**的位数。

**规则：固定位数零填充，按量级升位。**

- 以 **3 位零填充**起步：`T-001`、`T-002` … `T-099`、`T-999`（兼容既有历史 T-001~T-015）。
- 到达 `T-1000` 自然升为 **4 位**（`T-1000`…），再到 `T-10000` 升 **5 位**，依此类推，永不封顶。
- 同一量级内位数固定、排序稳定、可预期；位宽仅在进位点（999→1000→10000）自然扩张，**不在量级内做跨位对齐**（无须补零到统一宽度）。

**理由**：① 兼容既有 3 位历史，不折腾不对不上；② 位数固定满足可预期性；③ 不提前硬消费位宽——项目现实几十到几千任务，3 位起、最多自然长到 5 位，碰不到上限；④ 目标 ID 是哈希，与 T 编号无关，不存在"编号用尽"。

## 会话识别（用户只说三种话）

- 「描述一个问题 / 一个现象」→ 判定为新任务，建立分析任务并**并行跑**（用子代理，独立只读上下文，不占写锁，互不干扰）。
- 表达决定（「这个可以」「先做前两步」「暂停」「退回去」）→ 识别为决策：放行 / 裁剪 / 暂停 / 打回，**不当作新任务**。
- **对确认请求的答复**（存在未决 NEED-INPUT 时，「可以」「放行」「选 A」「先跳过」）→ 转发给对应后台代理或执行取消流程，**不当作新任务、不当作泛泛闲聊**。

其余闲聊、问为什么、要解释 → 正常作答，不建任务。

## 过程留痕（process journal，2026-08-29 新增，强制，CASE-015/016 回灌）

> `PIPELINE.md` 只存「摘要 + 队列 + 状态」（结论导向、轻量）。**过程信息**（需求原话 / 候选方案取舍 / 确认与仲裁理由 / 子代理事件时间线 / 中间产物路径）**另存**到项目本地、git 跟踪的 `.pipeline/journal/T-xxx.journal.md`。两级并存：
> **PIPELINE.md 管「做什么 + 做到哪」，journal 管「怎么做 + 为什么」。**

### 何时写（由主对话编排器在关键节点落盘；子代理产出事件也由编排器归并）

- **任务建立**：记需求原话（用户怎么说）、初始分析、候选方案与取舍。
- **每个审批门**：记该项的确认结论 + 理由（谁拍板、何时、为什么选这条即 NOT 那条）。
- **仲裁点**：记「选 X 不选 Y」的权衡依据（对应《需用户拍板》类条目）。
- **子代理事件**：把 `PROGRESS / NEED-INPUT / DONE / BLOCKED / FAILED` 追加到内置时间线（带时间戳、commit、验证结果、受阻原因）。
- **中间产物**：记该任务产出的设计文档 / 测试 / 迁移 / 脚本路径，便于崩溃后找回上下文。

### 内容模板

复制 `templates/JOURNAL.md` 为 `.pipeline/journal/T-xxx.journal.md` 后按节填。允许追加、不删历史段（保可追溯）。任务完成时在其头部打「✅ DONE」标记并保留全文，不因完成而清空。

### 与恢复的关系

崩溃 / session 丢失 / 后台进程死掉后，除读 `PIPELINE.md` 恢复「队列 + 状态」外，还要读对应 `.pipeline/journal/T-xxx.journal.md` 恢复**完整过程脉络**（需求原话、已确认/已仲裁的结论、中间产物路径），从而精确续跑：不重复已完成、不丢未定结论。

## 跨会话持久化

队列状态只在 `.pipeline/PIPELINE.md`（含事件日志区），**不在我的上下文里**；过程信息在 `.pipeline/journal/T-xxx.journal.md`（见上节）。会话中断/重开后，用户说「接上队列，继续跑」→ 读 PIPELINE.md 恢复写锁、已完成/排队/待审批列表与未读事件，并读对应 journal 恢复过程脉络，精确续跑，**不重复已完成任务、不丢未定结论**。为控制上下文膨胀，分析任务一律丢给子代理，我这边用于调度只读「活跃任务面板 + 当前任务的方案 + PIPELINE.md 状态行」+ 即时读出需要的 journal 片段。

## 首次使用（bootstrap）

在某个项目第一次用时：把本 skill 自带的 `templates/PIPELINE.md` 复制为 `<项目>/.pipeline/PIPELINE.md`；把 `scripts/lock.ps1`、`scripts/freshness.ps1`（本 skill 自带）复制到 `<项目>/.pipeline/`（与下方文件布局一致：脚本在 `.pipeline/` 根，无 `scripts/` 子层）；建 `<项目>/.pipeline/journal/` 目录并复制 `templates/JOURNAL.md` 为其规格说明（首次任务时再物化为 `T-xxx.journal.md`）；探测该项目可用的 verify 命令（读 package.json / 构建脚本），列给用户确认后写入 PIPELINE.md。之后该项目的队列就由这份文件驱动。

## 文件布局（每项目）

```
<项目根>/.pipeline/PIPELINE.md     ← 队列状态 + 事件日志（唯一事实来源，可提交 git）
<项目根>/.pipeline/journal/T-xxx.journal.md ← 过程留痕（可提交 git；见「过程留痕」节）
<项目根>/.pipeline/lock            ← 写锁（内容=任务id+时间戳）
<项目根>/.pipeline/lock.ps1        ← 锁的 status/acquire/release/check
<项目根>/.pipeline/freshness.ps1   ← 新鲜度门（git diff 基线..HEAD -- touches）
```

## 一致性护栏（自己也要遵守）

- 绝不在主对话内联执行任何超过一个即时动作的任务；派发后没有向用户回执，不算完成调度。
- 绝不在同一仓库同时派发两个执行任务；派发前先读 `lock`，占用则绝不派发。
- 在标记任务 done 前，确认 verify 已通过（或已转待人工验证）。
- 优先级：不阻塞用户 → 不产生脏代码 → 不炸队列。
